# Agent Query Before Code

## 原则
在中大型项目、长期维护项目或多模块项目中，Agent 在生成代码、修改代码、重构代码之前，应先查询项目知识层，而不是直接根据局部代码片段或当前对话内容动手实现。

## 背景
很多 AI 编程失败，不是因为不会写代码，而是因为在不了解系统边界、已有实现、架构决策和依赖关系的情况下过早开始编码。结果通常表现为：重复造轮子、破坏约定、越层调用、忽略历史决策，或在长任务中逐渐偏航。

## 适用场景
- 多模块、多服务、多前后端协作项目
- 已存在项目知识库、架构文档或符号图索引
- 需要长期由 Agent 参与维护的仓库
- 涉及重构、扩展、跨文件修改的任务

## 核心要求
1. 先查询，再编码
2. 优先查已有实现、依赖关系和设计边界
3. 发现信息不足时，先补检索结论，不直接猜测
4. 对跨模块任务，至少确认“在哪里改”“为什么在这里改”“会影响谁”
5. 如果知识层与代码层冲突，先记录冲突，再做最小范围修正

## 推荐查询顺序
建议 Agent 在编码前按以下顺序检索：

1. **任务定位**
   - 这个任务属于哪个模块、页面、服务或能力域
2. **已有实现**
   - 是否已有相似函数、页面、API、组件或工作流
3. **依赖关系**
   - 谁调用它，它调用谁，依赖哪些表、服务、状态或文档
4. **架构边界**
   - 这一层是否允许直接访问下一层，是否有明确分层限制
5. **历史决策**
   - 是否已有“不这样做”的原因，是否存在被否决方案
6. **变更影响**
   - 修改会影响哪些页面、API、模块或生成链路

## 最小查询清单
如果任务较小，至少回答以下问题后再写代码：
- 现有实现在哪
- 最近似的模式是什么
- 当前修改属于哪个层
- 是否有现成决策或原则约束
- 本次改动最小落点在哪里

## 在 PKG 中的含义
该原则要求 Agent 不把 PKG 当作被动参考资料，而应把它当作编码前置步骤的一部分。

也就是说，流程应从：

```text
任务 -> 直接读代码 -> 写代码
```

升级为：

```text
任务 -> 查询 PKG / 文档 / 符号图 -> 确认边界 -> 写代码 -> 回写知识
```

## 价值
- 降低重复实现概率
- 降低架构偏航概率
- 提高长任务一致性
- 提高对现有项目约束的遵守程度
- 让 Agent 从“局部补丁器”升级为“项目维护者”

## 代价与边界
- 会增加少量前置检索成本
- 小型一次性脚本未必需要完整查询流程
- 如果知识层过时，查询结果可能误导实现，因此需要持续回写与校验

## 实践要求
1. 对新增 feature，先找相似 feature、相似 API、相似页面
2. 对重构任务，先查调用链与影响范围
3. 对数据库相关任务，先查表、查询路径、已有读写点
4. 对 UI 生成任务，先查 Schema、生成器约束与已有模式
5. 对架构类任务，先查 decisions、principles、patterns

## 失败信号
如果出现以下现象，通常说明违反了该原则：
- 写完后才发现项目里已有同功能实现
- 新代码绕过了既有 API 或服务边界
- 重构后破坏了多个调用方
- Agent 给出的方案与已有决策明显冲突
- 每次任务都重新发明目录结构、接口形状或页面生成方式

## 与知识库的关系
推荐的映射关系：
- `knowledge/patterns/`：查常见结构与套路
- `knowledge/methods/`：查可执行流程
- `knowledge/decisions/`：查已采纳或已否决的关键选择
- `knowledge/principles/`：查跨主题通用约束
- `knowledge/inbox/`：查尚未定型但值得参考的原始材料
