# Shared State Over Session Memory

## 原则
在多代理协作、长任务执行或多轮修正流程中，应优先把任务状态、执行进度、反馈结果和关键约束保存在共享状态中，而不是依赖某个 Agent、CLI 会话或 daemon 进程的瞬时记忆。

## 背景
会话记忆的最大问题不是“容量不够”，而是它不稳定、不可审计、不可恢复，也无法天然在多个执行角色之间共享。对长任务来说，如果上下文主要存在于会话里，那么一旦重启、切换执行器、修改 prompt，系统就会退化为重新理解项目、重复决策和重复修正。

## 适用场景
- OpenClaw、Supervisor、cursor-agent 等多角色协作
- 需要多轮次推进的长任务
- daemon 进程可能重启或切换的执行系统
- 需要审计、回放、重试或恢复的自动化编程流程

## 核心要求
1. 任务状态必须外置，不能只存在于会话上下文里
2. 关键约束必须结构化存储，而不是只以自然语言提示出现一次
3. 执行结果必须可追踪，至少保留状态变化、结果摘要和工件索引
4. 任何角色都应把共享状态视为权威事实源，而不是把自己的上下文记忆视为权威
5. 会话只能作为临时工作内存，不能作为长期系统记忆

## 为什么共享状态更可靠
- **可恢复**：进程重启后仍能恢复任务
- **可审计**：可以查看是谁、何时、如何推进了状态
- **可共享**：多个角色能读取同一份事实源
- **可修正**：发现错误后可基于事实记录回滚或重试
- **可扩展**：后续可从单机流程升级到多 worker 或远程执行

## 推荐存储边界
建议这样划分：
- `共享状态`：任务状态、验收、反馈、工件索引、依赖关系
- `文件工件`：日志、patch、报告、大文本输出
- `会话上下文`：当前一步执行所需的临时工作记忆

不建议把以下信息只保留在会话中：
- 当前任务属于哪个 spec
- 当前任务状态
- 上一轮执行结果
- 修正意见
- 关键决策约束

## 在执行架构中的含义
如果系统采用：
- `OpenClaw` 做规划
- `Supervisor` 做执行监督
- `cursor-agent` 做代码执行

那么三者都应围绕共享状态协作，而不是围绕某个 daemon 的内部上下文协作。

也就是说：

```text
共享状态 = 权威事实源
会话上下文 = 临时执行缓存
```

## 推荐实现方式
第一版建议采用：
- `SQLite` 保存结构化状态
- `artifacts/` 保存日志与大对象

这种方式足够轻量，也足够可靠，适合本地和单机执行的 MVP。

## 失败信号
如果系统出现以下现象，通常说明过度依赖会话记忆：
- daemon 重启后任务状态丢失
- 不同 agent 对“当前任务是什么”理解不一致
- 修正意见只存在于聊天记录里
- 执行结果无法回放或审计
- 每次继续任务都要重新解释背景和约束

## 代价与边界
- 共享状态建模需要前期设计成本
- 如果状态模型过于复杂，会增加实现门槛
- 小型一次性任务不一定值得引入完整共享状态层
- 共享状态本身也需要治理，否则会出现脏数据与陈旧记录

## 实践要求
1. 每个 task 都应有稳定 ID 和状态
2. 每次执行都应记录事件或结果摘要
3. 反馈与修正意见要落到共享状态，而不是只留在对话里
4. daemon 设计必须允许基于共享状态恢复工作
5. 需要长期保留的上下文，应优先回写知识库或状态存储
